# 仕事設計OS｜ルウ王子版

スパイラル産業向けの独立した体験アプリです。初期データは全て仮想事例であり、実際の店舗、社員、取引先の情報や実績ではありません。

## 完成する仕事

業務の棚卸し、なくす・まとめる・AIへ任せる・再配置・人が担うの五分類、曜日・時間帯・場所・技能の照合、役割のたたき台、試行・育成、確認履歴、TXT／JSONでの引継ぎ。

採用しないことを正解にせず、採用前も採用後も仕事を見直します。候補者選考、性格・健康・退職可能性の推定、給与計算、求人の自動公開は行いません。

## 30秒のデモ

トップの「再設計の仮説を試す」を押す。対象業務が週47.5時間から約38.3時間に変わる。作業時間の差は550分／週（表示9.2時間）、技能・場所・時間帯を照合した未充足は450分／週（7.5時間）。

時間帯画面の比較で「遠隔の事務を追加・平日10〜13時」を選んでも未充足は7.5時間のまま。「現地の接客を追加・平日10〜13時」なら、この分割可能時間モデルでは0になる。どちらも週15時間の追加。比較案は保存される本案・役割資料には自動反映しない。

これは仮定に基づく計算例で、実績・必要人数・確定シフト・採用不要の証明ではありません。

## 計算モデル

曜日別、8〜18時の1時間枠。業務は1人分の作業として入力。並行して複数人が必要なら別業務へ分解する。flexは時間枠内で分割可能。coverageは各1時間枠に均等な対応量が必要なモデル。必要な技能、現地／遠隔の条件に合う担当枠だけへ接続し、最大流で分数を配分する。担当枠の使用量は一つの容量制約で管理し、複数の技能で二重使用しない。責任者判断を先に確保する探索順。

最適な役割分担が唯一とは限らない。連続して行う作業、分単位の発生タイミング、移動、法令や勤務・休憩の適合性はモデルに含めない。入力する容量は対象外業務と休憩を引いた対応可能時間。実シフトは現場で検証する。

削減時間は業務量の差。再配置だけでは時間を減らさない。AI案の人の確認時間は残作業時間の内数。初期設定・教育時間は初週の別枠として扱い、効果に自動で混ぜない。安全条件に反する案は元の業務条件で計算する。

## 保存と公開

保存キーは work-design-os:v1。同じブラウザのlocalStorageのみ。URL共有だけで入力内容は共有されない。JSONで持ち運び可能。共有DB、ログイン、同時編集は未実装。個人情報・機密は入力しない。

条件が変わると確認済み記録は旧条件になる。過去資料を20件まで保持し、上限を超えた場合は黙って上書きしない。JSONからの読込時には現行承認を解除する。端末内の確認履歴は改変不能な監査ログではない。

## AI接続の状態

アプリの計算・編集・保存はAI APIなしで動く。相談自由文を自動解釈しているとは表示しない。

任意のAI補助は /api/work-design-ai.js に実装。初期状態は無効。設定不足、認証不一致、送信元不一致、利用枠確認失敗ではOpenAIを呼ばない。公開時に設定変更権限を取得できなかったため、実APIでの推論は未検証。

管理者がVercelの該当プロジェクトで以下を設定し、再デプロイする。キーやアクセスコードを公開ファイルやチャットに貼らない。

| サーバー側環境変数 | 内容 |
|---|---|
| OPENAI_API_KEY | OpenAIの秘密キー |
| WORK_DESIGN_ACCESS_CODE | 管理者がランダム生成する24〜128文字の招待コード。共有デモ用であり、企業向け認証の代替ではない |
| WORK_DESIGN_ALLOWED_ORIGIN | 許可するHTTPSオリジン。例 https://ruu-first-app.vercel.app 。末尾スラッシュなし |
| UPSTASH_REDIS_REST_URL | 管理下の継続利用できるUpstash Redis REST URL。期限付き試用DBを使わない |
| UPSTASH_REDIS_REST_TOKEN | 上記Redisの書込みトークン |
| WORK_DESIGN_MODEL | 任意。既定 gpt-4.1-mini |

この操作ではアカウント作成・課金開始・環境変数変更は行っていない。デモの実API使用料とホスティング・Redisの利用料は別途契約に従う。

アプリ全体で1日20回・1カ月200回、入力24,000バイト、出力4,000トークン、タイムアウト、サーバー側同一リクエストの5分間重複防止。利用枠はRedisのLuaスクリプトで原子的に予約し、複数インスタンスで共有する。失敗時も予約枠は戻さない。無制限な課金を防ぐため、Redis不通なら停止する。金額そのものの完全な請求上限ではなく、呼出し数とサイズの上限。ホスティングへの攻撃や招待コード漏洩への対策は、公開規模に応じて追加する。

AIは仕分け・理由・小さな試行・確認条件を返す。数値は変更しない。構造化出力と業務IDを検証し、現地対応や重要判断をAIへ移す案はサーバー側でも止める。外部資料内の命令を指示として扱わない。ツール実行は与えない。

送信するのは相談と対象業務の限定フィールド。担当名・対応時間表・観察記録は送らない。アクセスコードはブラウザ保存しない。OpenAI Responses APIのstore:falseを指定するが、これだけで全ての保持がゼロになるという意味ではない。実データ利用前に双方の契約とデータ保持条件を確認する。

## 検証と限界

ソースのNode構文検査、計算エンジンの境界値・容量不変条件、APIの認証・停止条件・不正応答、ChromiumのUI操作を検証。

制作環境のChromiumではlocalhostへの接続が管理ポリシーでブロックされるため、UI検証は同一ソースをページへ読み込み、localStorageと通信をテスト用アダプターに置き換えて実施。再読込・書出し・エラー処理はこのアダプター上の検証であり、実公開ドメインのストレージや通信を確認したものではない。公開画面・実API・実Redis・本番CSP・端末ごとの永続保存の確認は別途必要。
